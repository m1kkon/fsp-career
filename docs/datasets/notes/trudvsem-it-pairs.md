# «Работа России» (opendata.trudvsem.ru): IT subset of real candidate↔vacancy interactions — quantified

Measured 2026-10-08/09. All numbers below come from **streaming the official files end-to-end** (current response and invitation feeds, vacancy.json, the 2025-08-13 national vacancy XML, 2025-01-01 regional vacancy XMLs, and 3 historical response snapshots) or from **HTTP-Range random sampling** (cv.json, Kaggle CSV). Extrapolations are labelled **[EXTRAPOLATION]**. Scripts and summaries are in [`../trudvsem/`](../trudvsem/) (`parse_inter.py`, `parse_json.py`, `sample_cv.py`, `classify.py`, `join.py`, `join_summary.json`, `inter_summary.json`); ID-level `*_ids.tsv.gz` files are regenerated by the scripts and not stored. No PII was written to these notes.

**IT classifier used everywhere** (`classify.py`, keyword regex over vacancy title `vacancyName` / CV title `positionName`, plus the portal sphere code `codeProfessionalSphere = InformationTechnology`):
- **core IT** = our profile: программист / разработчик / developer / инженер-программист / frontend / backend / fullstack / python / java / php / C++ / C# / .NET / android / iOS / верстальщик …, QA / тестировщик, DevOps / SRE, data scientist / аналитик данных / data engineer / ML / нейросети / ИИ. **1С titles are excluded from core and counted separately**; CNC/ЧПУ, РЭА, конструктор, преподаватель, редактор are excluded.
- **IT sphere** = portal sphere code «Информационные технологии, телекоммуникации, связь» (broad: includes telecom, support, sysadmins, couriers of telecom firms etc.).
- Keyword classification is approximate (some industrial «инженер-программист» are embedded/automation roles; a few false positives/negatives remain).

## Q1. Distinct values of responseType / candidate / manager / isNew / deleted; meaning; date range; record counts

### Takeaway
Both feeds are a rolling **2-year window (2024-10-08 → 2026-10-08)**: **1,039,573 «response» records** and **3,639,201 «invitation» records**. Only the «response» feed carries an outcome (`responseType` ∈ {Приглашение 514,084; Отказ 512,320; Принятие 13,169}); in the «invitation» feed `responseType` is constant «Отклик» and `deleted` is constant in both feeds. Behavioural evidence strongly suggests that, despite the feed names, the **«invitation» feed records are candidate applications (отклики)** and the **«response» feed records are employer reactions** (Отказ = rejection of an application, Приглашение = employer invitation, often bulk/proactive, Принятие = acceptance after an invitation). The portal does not document the semantics, so this is an inference.

- **Behavioural evidence (computed from the two full streams)** — [response XML](https://opendata.trudvsem.ru/7710538364-response/data-20261008T100844-structure-20161130T143000.xml), [invitation XML](https://opendata.trudvsem.ru/7710538364-invitation/data-20261008T100844-structure-20161130T143000.xml):
  - dateModify == creationDate for 96.8% of Отказ, 97.6% of Принятие, but only 20.4% of Приглашение (median later modification of Приглашение: 32 days). → Отказ/Принятие are immutable "event" records.
  - 458,625 of 512,320 Отказ records (89.5%) have an invitation-feed record for the **same (idCv, idVacancy)**; 99% of those Отказ are created **after** it (median +2.2 days, p10 +0.03 d, p90 +20.6 d); for 148k of them the invitation-feed record's dateModify equals the Отказ creation time (±60 s). Only 13% of Приглашение and 32% of Принятие have such a match.
  - Within the response feed, multi-record pairs follow sequences «Приглашение→Отказ» (41,083 pairs) and «Приглашение→Принятие» (9,530); ~80% of Принятие follow a Приглашение.
  - Burst test: 25.4% of Приглашение records are in "vacancy bursts" (≥3 different CVs for the same vacancy in the same minute) vs 0.1% in "CV bursts" → employer-initiated, often mass invitations. Invitation-feed «Отклик» records show the opposite tilt (4.1% CV-bursts vs 1.5% vacancy-bursts) → candidate-initiated, like applications.
  - In the invitation feed the employer side archives 50% of records (`manager` Не активен) vs candidates 14% — consistent with an employer inbox of received applications.

### Inferences
- Most coherent reading: **invitation feed ≈ candidate→vacancy applications** (responseType literally «Отклик (соискателя)»); **response feed = employer decisions**: «Отказ» = employer rejected the application (negative), «Приглашение» = employer invited the candidate (positive; ≥87% are not preceded by an application record → largely *proactive* invitations, i.e. reverse recruiting), «Принятие» = acceptance after an invitation (strong positive; plausibly the candidate accepting / being hired). Under an alternative reading Отказ could partly be candidates declining invitations; the 89.5% application→Отказ linkage makes "employer rejection of an application" the more likely majority meaning.
- `isNew` = viewed/unviewed by the receiving side (weak "viewed" signal); `candidate`/`manager` = archived or not in each party's cabinet; `deleted` carries no information (deleted items are simply not published).
- Practical labels for us: positive = Приглашение ∪ Принятие; negative = Отказ; application without any reaction = "applied, no feedback" (implicit/unlabelled). This is also how the HSE/Kaggle derivative labels it (Приглашение=1, Отказ=0).
- The "no pending/under-review state" and the immutability of Отказ mean timing features (time-to-decision) are available for negatives and partially for positives.

### Gaps
- The portal publishes no data dictionary explaining responseType semantics or who performs «Отказ»/«Принятие»; trudvsem.ru/opendata pages returned HTTP 460 from this machine (geo/anti-bot block), so the official description could not be read. Semantics above are inferred.
- The current files keep only 2 years. Older interactions come from historical daily snapshots on the same server (back to 2021-02-10; see Q2) or from RCSI (2020-08-16 → 2021-10-30).

## Q2. How many responses/invitations involve IT vacancies and/or IT CVs; how resolvable are idVacancy / idCv in the dumps

### Takeaway
The **current vacancy.json (499,817 vacancies) alone resolves only 17.5% of response records and 13.0% of invitation records** (it holds only currently active vacancies), whereas **cv.json resolves ≈95% of interaction CV ids** [sampled]. **But the portal also serves daily historical XML snapshots** (vacancies by federal district back to 2021-02-10, national back to 2026-07-01 plus a stale 2025-08-13 full file; CVs back to 2023-10-06; responses/invitations back to 2021-02-10). Adding just two older vacancy snapshots (2025-08-13 national + 2025-01-01 regional) raises resolution to **48.8% of responses / 36.1% of invitations**. With these three snapshots the text-joinable core-IT set is: **4,572 employer-reaction records (4,050 Отказ / 490 Приглашение / 32 Принятие) on 1,195 IT vacancies**, **15,982 application records on 3,571 IT vacancies** (13,691 distinct application pairs → 3,400 Отказ, 163 Приглашение/Принятие, 10,128 no reaction), and **287 proactive-invitation pairs** (11 → Принятие). So the **labelled IT set is ≈3.6k application→outcome pairs (~95% negative)** plus ~10k unlabelled applications; positives are in the low hundreds. Over the full 2 years, core-IT activity is roughly **9–14k employer reactions and 32–60k applications [EXTRAPOLATION]**; more snapshots would recover most of their vacancy texts. 1С is a separate, smaller slice.

### Inferences
- **What we can build with texts on both sides, using only the 3 snapshots already tested**: ≈4.6k employer-labelled IT reaction records (≈3.6k distinct application→outcome pairs, ~95% Отказ) + ≈10k IT application pairs without explicit outcome + ~290 proactive IT invitations (≈11 accepted). The ~95% CV resolvability barely changes this. Real, but small and very imbalanced; IT positives number in the hundreds.
- Full-window estimates of core-IT activity: share-based from the resolved part ≈9.4k reactions / ≈44k applications (3 snapshots) or ≈11.8k / ≈59k (current dump only); CV-side sampling ≈13.9k / ≈31.6k **[EXTRAPOLATION]**. Iterating over monthly regional snapshots (≈9 × 75–106 MB gzip per date) should push vacancy resolution well above 50%, and stitching historical response/invitation snapshots extends the history to 2016–2021 and 2022–2024 (the history is uneven: some old snapshots contain only Отказ/Принятие or only Принятие).
- Going forward, snapshotting daily (as RCSI did weekly) captures nearly all vacancies before they are archived.
- 1С (≈1.1k vacancies across 3 snapshots, 1,180 reactions, 3,420 applications) should be kept out of the core set or used as an extra class.

### Gaps
- cv.json was sampled (1.09%), not fully streamed (44 GB at ~1 MB/s ≈ 11–12 h); CV-side IT counts and resolvability are estimates with sizeable sampling error.
- Only 3 vacancy snapshots were joined; ~51% of response and ~64% of invitation records still lack vacancy text in this analysis (more snapshots would reduce this; not done for time).
- Historical invitation snapshots were not streamed; the composition changes in historical response snapshots are unexplained.
- Keyword classification has some noise (embedded/industrial "инженер-программист", ИИ-related titles).

## Q3. Field-by-field mapping to our product fields; fill rates for IT records; example IT pairs

### Takeaway
Trudvsem CV/vacancy JSON maps reasonably to our schema: title, salary, experience, schedule/employment, education, region, skills list and multi-paragraph requirements/responsibilities exist; **grade, specialization, team context, nice-to-have and an "about me" field do not exist** and must be derived. Text richness is modest: IT vacancies have ~175-char requirements and ~320-char responsibilities; IT CVs rely on a portal skill checklist (`skills`, 23% filled) and short work-history "demands" (62% of CVs have work history; median 154 chars).

### Cited Findings

### Inferences
- Vacancy text is the stronger side: `responsibilities` + `requirements` give a usable job description; stack must be extracted from free text (structured `hardSkills` is 2% filled).
- CV text for IT candidates is thin: skill checklists + short demands; no "about me". Our richer fields (grade, specialization, team context, nice-to-have, work format) need NLP derivation or remain empty.
- `experience` is total career years, not domain years (example 3) — mapping to our "years of experience in IT" requires the work-history list.
- The population skews to state/municipal employers, regions and career switchers; it resembles the hh.ru "junior / regional" tail rather than the Moscow product-IT market our product targets.

### Gaps
- CV fill rates are from 1,011 sampled core-IT CVs (not the full dump).
- Whether `isNew` really means "viewed" is undocumented.

## Q6. License / terms of trudvsem open data

### Takeaway
meta.csv has no license field and the portal's terms page (trudvsem.ru/opendata) was unreachable (HTTP 460) from this machine. The datasets follow the Russian government open-data standard v3.0, which requires free, contract-free use incl. commercial, with attribution to the source; the licence field itself is optional.

### Cited Findings
- meta.csv for response/invitation/cv contains standardversion «http://opendata.gosmonitor.ru/standard/3.0», creator «Портал Работа в России», no license property — [response meta](https://opendata.trudvsem.ru/7710538364-response/meta.csv), [cv meta](https://opendata.trudvsem.ru/7710538364-cv/meta.csv)

### Inferences
- Using the data for a hackathon prototype with attribution («Источник: портал «Работа России», opendata.trudvsem.ru») is consistent with the open-data standard; personal data present in the dumps (despite the descriptions) still falls under 152-ФЗ, so derived training sets should be de-identified.
