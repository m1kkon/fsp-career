# Целевой грейд и задания на кодинг

Актуально для версии исходников на 10 октября 2026. Перед комплексным тестом кандидат выбирает Junior, Middle или Senior на странице начала теста. После старта выбор фиксируется в попытке. Обычные навыки остаются без выбора целевого грейда и не подтверждают основную категорию резюме. Состав адаптивных частей не упрощается при выборе более низкого грейда: целевой уровень определяет трактовку результата. Старый сценарий предварительной записи сохранён в API для совместимости, но текущий интерфейс запускает сегодняшний пул напрямую.

## Состав ролей

| Роль | Обязательные обычные модули | Интеграционный модуль |
|---|---|---|
| Backend Developer | Python, SQL, Backend/API | `integration-backend` |
| Frontend Developer | JavaScript/TypeScript, HTML/CSS и браузер, React | `integration-frontend` |
| QA Engineer | Тест-дизайн, SQL, Автоматизация тестирования | `integration-qa` |
| DevOps Engineer | Инфраструктура, Python | `integration-devops` |
| Data Scientist | Python, SQL, Статистика и анализ данных, Машинное обучение | `integration-ds` |
| ML Engineer | Python, Машинное обучение, ML Engineering | `integration-mle` |

Между модулями суточного пула предусмотрена пауза 60 секунд. Общее время зависит от числа обязательных модулей и экспериментальных позиций; это не один короткий тест для всей роли.

## Исходы роли

Результат роли вычисляется после всех модулей и интеграционного блока:

- Выбранный грейд и следующий достигнуты: **выбранный грейд+ подтверждён · потенциал следующего**.
- Выбранный грейд и его «+» достигнуты, следующий не достигнут: **грейд+ подтверждён**.
- Выбранный грейд достигнут без «+»: **грейд подтверждён**.
- Выбранный грейд не достигнут, нижний достигнут: **выбранный не подтверждён · подтверждён нижний грейд**, с «+», если достигнут и его порог.
- Даже Junior не достигнут во всех модулях: **выбранный грейд не подтверждён**, без присвоения нижнего.

Порог «+» для каждого модуля — середина между порогами грейда и следующего. Для Senior — середина между порогом Senior и 100. При действующих стандартных порогах **40/60/85** это Junior+ 50, Middle+ 72,5, Senior+ 92,5. Нестандартные пороги сохранённой спецификации меняют эти середины. Кроме общего балла, проверяются отдельные требования теории и практики из [scoring.md](scoring.md). Каждый обязательный модуль и интеграционный модуль должны выполнить соответствующее требование. Высокий балл в другой области не компенсирует недостаточный. Потенциал следующего показывается только при фактическом достижении всех его требований.

Правило `target-grade-five-outcomes-evidence-v3` фиксируется при старте. Пороги и основание «+» сохраняются в результате. Старые попытки без этого правила сохраняют прежний отчёт. Пять исходов видны в карточках ролевых тестов и разделе результатов. Основная категория резюме подтверждается только завершённой ролью; изменение уже подтверждённой категории ограничено 90 днями, а более слабый повторный результат в той же специализации её не понижает. Балл профиля при применении результата — минимум итоговых баллов обязательных модулей.

## Формат прохождения

Вариант обычного вопроса можно выбрать кликом по карточке или клавишами 1–4. Выбор и корректный числовой ответ сохраняются без перехода; «Ответить» или Enter открывают следующий вопрос. Если таймер истёк, в зачёт остаётся последний ответ, который сервер успел сохранить. Кодовый черновик сохраняется отдельно и требует явной отправки на проверку. Условие и код отображаются раздельно; технические имена и выражения выделяются моноширинным шрифтом.

Каждый новый модуль состоит из двух адаптивных частей по 16 зачётных заданий. В каждой — 14 обычных вопросов и 2 задания формата `coding`, по 300 секунд каждое. Кодинг занимает 5-ю и 12-ю позиции внутри части, отдельного хвоста практики нет. Обычные вопросы по умолчанию имеют лимит 20 секунд: общая длительность модуля — 1760 секунд (29 мин 20 с), без экспериментальных позиций.

Правило `two-stage-16-mixed-coding-v3` фиксирует распределение сложности для всех 16 заданий, включая кодинг. В первой части кодинг имеет сложность 2; в базовой второй части — 1, в повышенной — 3. Первая часть оценивается по общей шкале сложности с частичным зачётом кодинга: повышенная ветка открывается при результате ≥65 **и хотя бы одной полностью решённой задаче кодинга первой части**. Иначе выбирается базовая ветка. Состав обеих веток сохраняется до старта. Семейства не повторяются на выбранном пути. Правило маршрутизации и версия итогового оценивания — отдельные идентификаторы.

Оценивание `rasch-theory-practice-v3`: теория составляет 60% итогового балла, кодинг — 40%. За каждую задачу кодинга начисляется доля пройденных проверок лучшей отправки. Балл кодинга учитывает сложность фактических задач; сырой средний зачёт показывается отдельно. Каждый грейд дополнительно требует минимум балла кодинга (Junior 30/100, Middle 50/100, Senior 75/100) и полностью решённую задачу сложности не ниже 1/2/3 соответственно. Для «+» минимум балла кодинга — 60/80/90 из 100. Эти требования действуют для каждого обычного и интеграционного модуля. В каждом грейде действует минимум теории (35/55/75). Пороги предварительно настроены на синтетическом development-наборе; реальную эмпирическую калибровку не заявляем. Формулы, ограничения и версии описаны в [scoring.md](scoring.md).

В банк добавлены шесть разных семейств кодинга для каждого из 18 модулей: по два каждой сложности. Вопросы сохранены заранее, а не генерируются при прохождении. Для JSON-ответов сравнивается разобранная структура, без зависимости от пробелов и порядка ключей; массивы сохраняют значимость порядка. SQL/Bash проверяются по фиксированному выводу, HTML/CSS/React используют структурные проверки результата.

Новые спецификации применяются к новым попыткам. При переходе на смешанный формат создаётся новая версия суточного пула с суффиксом `-mixed-v6-coding-difficulty`; прежний пул этой даты, начатые попытки и завершённые оценки не переписываются. Старые спецификации и попытки продолжают использовать исходные правила.
Редактор поддерживает Tab для отступов и Ctrl/⌘+Enter для запуска на текущем вводе, автосохранение в попытке и отдельный таймер. Закрытые проверки и их ключи не отправляются клиенту. Слева от редактора расположены редактируемый ввод (по умолчанию — первый пример) и вывод. «Запустить» выполняет код один раз только на текущем вводе; проверки и их ключи при этом не используются. «Отправить» проверяет все тесты на сервере и сохраняет отправку без перехода к следующему вопросу. На вопрос разрешены три отправки; счётчик и результат последней отправки (зелёный/красный сектор на каждый тест) сохраняются в попытке. В зачёт идёт лучшая отправка; редактирование черновика её не перезаписывает. «Далее» и истечение таймера закрывают вопрос без дополнительной проверки. Несданный код не оценивается. Повтор идентификатора отправки не расходует попытку, а конкурирующие запросы защищены проверкой ревизии. Подделать правильность ответом клиента нельзя. LLM не оценивает решения.

Песочница доступна по `/sandbox` с примерами. Языки: Python, JavaScript, TypeScript, PostgreSQL SQL, Bash, HTML, CSS и React/TSX. Для статистики/ML используется Python; установленная среда содержит стандартную библиотеку. HTML/CSS/React могут показываться в iframe без скриптов и сети. Для новых HTML/CSS/React-заданий используются структурные `markupRule`: DOM, атрибуты и CSS-декларации. Проверка по подстроке `contains` для новых заданий запрещена; старые снимки сохраняют исходную проверку.

## Локальный запуск

```sh
docker build -t fsp-code-sandbox:local sandbox
npm run dev -- --hostname 127.0.0.1 --port 4173
```

Для обычного прохождения дополнительная ручная сессия не нужна: [суточный пул](daily-question-pools.md) создаётся автоматически. Для отдельной административной сессии со всеми модулями, двумя заданиями на кодинг в каждой части по 5 минут:

```sh
node --env-file=.env.local scripts/prepare-coding-session.mjs
```

Скрипт создаёт и публикует отдельную сессию на 48 часов, открывающуюся через 10 секунд. Новые версии спецификаций создаются только для модулей, где ещё нет двух задач на часть по 300 секунд; существующие опубликованные сессии и попытки не меняются. Это сценарий старого API с выбором сессии: текущий интерфейс по `targetId` продолжает использовать суточный пул. Скрипт требует настроенной PostgreSQL; параметры приложения и миграции описаны в [deployment.md](deployment.md).

## Условия и примеры задач

У всех заданий на кодинг есть `coding.inputFormat`, `coding.outputFormat` и `coding.examples` — массив объектов `{input, output, explanation?}`. Они отображаются над редактором и в отдельной песочнице. Для новых вопросов мейнтейнер обязан заполнить оба формата и хотя бы один пример; эти данные сохраняются в версии вопроса и снимке варианта.

Для алгоритмов описаны JSON-структуры и тип результата, для SQL — исходные таблицы и строки результата запроса, для Bash — текстовые записи. HTML/CSS описывают исходную и ожидаемую разметку. React-задачи могут принимать JSON-пропсы через stdin; результат проверяется как разметка. Примеры существующих числовых и текстовых задач соответствуют открытым проверкам; точное форматирование вроде `2.00` сохраняется. Для старых снимков без этих полей описание и примеры восстанавливаются только из открытых проверок: закрытые случаи не раскрываются, состав варианта и оценивание не меняются.

## Изоляция и размещение

Код выполняется только в отдельных Docker-контейнерах: без сети, host mounts и дополнительных capabilities, с read-only rootfs, непривилегированным UID, ограничениями CPU, памяти, процессов, времени и вывода. Данные теста идут через stdin; ожидаемый результат остаётся в контролирующем сервисе. Образы заранее собираются, на каждый запуск их скачивание запрещено. При отсутствии Docker выполнение возвращает понятную ошибку и не заменяется запуском на хосте.

В production web-контейнеру не следует выдавать Docker socket. На выделенном Docker-хосте запустите `scripts/code-sandbox-server.mjs`, задав `CODE_SANDBOX_TOKEN` (минимум 32 символа), `CODE_SANDBOX_HOST` и `CODE_SANDBOX_PORT` (по умолчанию 4180, 127.0.0.1). У web-приложения задайте `CODE_SANDBOX_URL` и тот же `CODE_SANDBOX_TOKEN`. Сервис должен оставаться в приватной сети; при переходе между хостами использовать HTTPS. Docker сам по себе не заменяет изоляцию отдельного хоста для публичного выполнения недоверенного кода.

Для размещения через `compose.yaml` параметры `CODE_SANDBOX_URL` и `CODE_SANDBOX_TOKEN` задаются в приватном `.env` вместе с настройками PostgreSQL и почты. Скрипт выпуска сохраняет их при обновлении приложения. Docker worker запускается отдельно; Compose приложения не создаёт его автоматически. Публичный `/api/code-sandbox` разрешает запуск только после входа и ограничивает его до 20 запросов в минуту на аккаунт. Демонстрационный режим включается только явным `FSP_DEMO_MODE=1`; в production его следует оставлять выключенным.

```sh
CODE_SANDBOX_TESTS=1 node --test tests/code-runner.test.mjs tests/assessments.test.mjs
```

Здесь необходимы доступный Docker, собранный образ и тестовая PostgreSQL. Обычный запуск тестов без `CODE_SANDBOX_TESTS=1` пропускает проверки реального исполнения кода. Последняя полная локальная проверка имела 13 таких пропусков; её нельзя выдавать за подтверждённый запуск песочницы. Актуальные результаты и ограничения: [grade-hardening.md](grade-hardening.md), [validation.md](validation.md).
