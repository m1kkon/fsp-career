# ФСП Карьера
Сопроводительная документация решения по специальному треку ФСП. Архитектура, механики, процедура валидации, интеграции и инструкция запуска.

Дата документа: 11 октября 2026 года.

ФСП Карьера - веб-платформа обратного найма ИТ-специалистов с подтверждением квалификации. Документ описывает пользовательские сценарии, компоненты, алгоритмы оценки и подбора, результаты проверок, интеграционные контракты и воспроизводимый запуск.

Исходный код: https://github.com/m1kkon/fsp-career. Прототип: https://fspcareer.space. Версия опубликованного приложения доступна в поле `revision` ответа `/api/health`.

## 1. Назначение и функциональная архитектура
Платформа реализует обратный найм ИТ-специалистов. Кандидат подтверждает квалификацию тестированием, а работодатель описывает потребность, получает объяснимую подборку и первым направляет предложение с зарплатой. Классические вакансии и самостоятельные отклики существуют как дополнительный канал, не заменяя обратный найм.

### 1.1. Сценарий кандидата
Кандидат регистрируется с подтверждением email, заполняет резюме и согласия, проходит анкету по отрасли, специализации и формату работы, выбирает предполагаемый грейд и проходит опубликованные модули роли. Результат теста определяет подтверждённую категорию для каталога работодателя. Предполагаемый, подтверждённый и потенциальный грейд отображаются как разные сущности: сильный результат на Middle не делает профиль автоматически Senior.

Резюме редактируется вручную: ФИО, контакты, стек, опыт, роли, навыки, языки, проекты и ссылки. Сервер формирует стандартизированный PDF. Частичное сохранение меняет только переданные поля; отсутствие поля не является командой удалить раздел. Для ввода резюме используется структурированная ручная форма; PDF является форматом выгрузки профиля.

Кандидат видит только свои приглашения, отклики, ответы на задания и тестовые результаты. Он принимает или отклоняет предложение, управляет публикацией профиля и историей ФСП. Сервис работает и без ФСП ID, и с пустой историей событий.

### 1.2. Сценарий работодателя
Работодатель заполняет профиль компании, описывает команду и потребность обычным текстом, затем подтверждает извлечённые ограничения: специализацию, минимальный грейд, обязательный и желательный стек, опыт, формат, город, зарплатный бюджет. Требование не считается обязательным только потому, что парсер распознал слово: пользователь проверяет форму.

Каталог показывает категории и кандидатов с краткими причинами соответствия. Работодатель уточняет запрос и сохраняет подборки. Приглашение можно направить без публикации вакансии. Компания, текст предложения, контакт компании и положительный диапазон зарплаты от-до в рублях доступны кандидату до согласия на контакт.

Работодатель публикует и редактирует вакансии, получает самостоятельные отклики, создаёт короткие практические задания, проверяет ответы и оставляет обратную связь. Первоначальное условие сохраняется вместе с ответом: последующее редактирование задания не переписывает историю решения.

### 1.3. Согласованный контакт и видимость
До принятия приглашения или самостоятельного отклика контакт кандидата скрыт от конкретного работодателя. Раскрытие не является глобальной публикацией контактов. На сервере проверяются роль, владелец и участники диалога; интерфейсные ограничения не являются единственным средством защиты. Статусы отправки, просмотра и решения доступны обеим сторонам по своим записям.

Приложение построено как модульный монолит с явным разделением интерфейса, API, бизнес-логики и хранения. API, правила подбора и исполнительный сервис можно масштабировать отдельно. Транзакции защищают изменения бизнес-записей; исполнение пользовательского кода происходит вне общей блокировки базы, с проверкой актуальности попытки перед сохранением результата. Повторная доставка того же ID и исходного кода идемпотентна; изменение исходника или закрытие попытки не позволяет применить устаревшее решение. Параллельное выполнение на worker ограничено четырьмя запросами, ответы worker валидируются сервером.

Compose ограничивает память основных сервисов: приложение 1536 MiB, PostgreSQL 768 MiB, Caddy 256 MiB, одноразовая миграция 256 MiB. Это лимиты конфигурации, не измеренное потребление под нагрузкой. Отдельному sandbox нужны собственные ресурсы; ёмкость сервера определяется с учётом числа одновременных исполнений и результатов нагрузочных измерений.

## 3. Механика тестирования и категоризации
### 3.1. Разные формы при сопоставимых правилах
Для основных ИТ-направлений задан справочник ролей и обязательных модулей. В банке 2359 записей, из них 559 задач с кодом, включая 10 выведенных из использования. Число записей не равно числу одновременно активных заданий. Структурный аудит проверяет ID, варианты, ключи, ограничения и заданные проверки, а не исполняет эталонные решения.

Модуль состоит из двух частей; используются выборки из семейств задач и адаптивные ветки. Шаблон, версия правил, состав предъявленной формы и порядок фиксируются сервером для начатой попытки. Ключи ответов не выдаются чужим пользователям. Ежедневные пулы, версия банка, разнообразие форм и кодинг затрудняют распространение единого списка ответов. Общие модули позволяют сопоставлять одинаковые компетенции между ролями.

Разнообразие форм и скрытые проверки уменьшают пользу заранее распространённых ответов. Внешняя помощь и утечка банка остаются ограничениями подхода; биометрический прокторинг не используется. Статистический анализ аномалий предусмотрен для дальнейшего развития системы контроля.

### 3.2. Оценка, подтверждение и повторное прохождение
Политика `rasch-theory-practice-v3` объединяет 60% теории и 40% практики с поправкой на сложность предъявленных заданий. Кроме общего порога применяются минимумы обеих частей и требование полностью решённой задачи нужной сложности по обязательным модулям. Сырой процент решения кодинга показывается отдельно от нормализованного результата.

Грейд не понижается принудительно. Не подтвердив выбранный уровень, кандидат получает объяснение и возможность выбрать следующий тест на подходящий уровень; уверенное прохождение даёт рекомендацию попробовать выше. Потенциальный более высокий уровень не заменяет подтверждённый. Смена подтверждённого грейда ограничена интервалом 90 дней. Старые результаты и начатые попытки сохраняют исходные спецификации, не пересчитываются новым алгоритмом задним числом.

Категория работодателя строится по специализации и подтверждённому тестом грейду. Стек и стаж резюме остаются заявленными данными и не превращаются в подтверждённые компетенции. Политика, время, баллы, рекомендации и история доступны владельцу профиля.

Теория оценивается через модель с логистической вероятностью решения: `logistic(x) = 1 / (1 + exp(-x))`. Для предъявленных заданий с якорями сложности b численно определяется параметр θ из уравнения `sum logistic(θ - b) = число правильных ответов`; итог теории равен `100 x logistic(θ)`. Практика использует аналогичное уравнение с частичным зачётом скрытых проверок и собственными якорями сложности. Итог объединяет 60% теории и 40% практики, после чего применяются минимумы обеих частей и ограничения задач соответствующего уровня. Якоря сложности являются предварительной авторской калибровкой, а не параметрами, оценёнными на независимой популяции людей.

### 3.3. Вакансии и регулярная практика
Связь роли, компетенций, модулей и банка позволяет показать выбор заданий на нескольких описаниях вакансий. Примеры из текущего справочника ролей `lib/question-bank.mjs` приведены ниже; каждый набор включает интеграционное задание, связывающее навыки роли. Для каждой опубликованной роли фактический состав определяется спецификацией, а не произвольным генерированием вопросов нейросетью.

| Пример потребности | Модули роли и интеграция |
|---|---|
| Middle backend: Python, PostgreSQL, сервисы и API | backend-developer: python, sql, backend; integration-backend. |

| DevOps: инфраструктура, контейнеры, Python-автоматизация | devops-engineer: infrastructure, python; integration-devops. |


«Задание недели» вычисляется сервером с интервалом 7 дней; предложение стабильно в рамках периода и не включает уже отвеченные задания. Периодические короткие задания компаний являются отдельной практикой: предложение учитывает специализацию и уже отвеченные задачи, кандидат видит историю, компания даёт оценку и обратную связь. Проверенная практика обновляет сигнал актуальности профиля, но не присваивает подтверждённый грейд и не подменяет основной тест. Изменённое/снятое задание не уничтожает исходное условие ранее отправленного ответа.

## 4. Механика подбора и NLP
Основной порядок опирается на подтверждённую категорию, а не на самостоятельно записанный Senior в резюме. Требования работодателя проверяются с исходами `pass`, `unknown`, `fail`; неизвестная готовность к переезду не считается доказанным отказом. Минимальный грейд Middle допускает подтверждённого Senior. Зарплатные диапазоны сопоставляются по пересечению, включая совпадающую границу.

Внутри соответствующих категорий рейтинг отражает потребность: специализация до 25, минимальный грейд 15, стек 12, опыт и проекты 20, тест 12, ФСП 6, формат 4, зарплата 4, предметная область 2; максимум 100. Это объясняемые веса MVP, не вероятность успешного найма. Рядом с баллом приводятся причины и пропуски данных. Без заданной потребности показывается отдельная сила подтверждённого профиля: тесты и ФСП, до 18.

Словарная NLP-нормализация технологий и правиловой анализ текста извлекают стек, типы задач, опыт, отрицания, пожелания и планы. «Не работал с X» и «планирую изучить X» не подтверждают практический опыт. Цитаты служат основанием объяснения. Уточнение формы явно заменяет извлечённые поля, в том числе очищает их. Текстовый компонент объединяет канонические свидетельства задач/технологий и ограниченное лексическое дополнение по утвердительным описаниям выполненной работы. Если каноническая доля c и нормированная TF-IDF близость l, итоговая доля равна c + 0,5 × (1 - c) × sqrt(l): лексика восполняет не более половины остатка текстового компонента. Отрицания и планы не становятся свидетельствами выполненной работы. Сравнительный TF-IDF baseline использует полный профессиональный текст; обученная нейросетевая модель и embeddings в рабочем ранжировании не используются.

## 5. Процедура валидации и результаты
Процедура объединяет программные и интеграционные проверки, контролируемый симулятор с авторской эталонной разметкой и отдельный benchmark реальных текстов. Для каждого измерения различаются проверяемая реализация, источник данных, объём выборки и область применимости результата.

### 5.1. Программные и интеграционные проверки
В GitHub Actions на ревизии `36c4e8e` выполнены **526 тестов: 526 прошли, 0 ошибок, 0 пропусков**. [Журнал проверки](https://github.com/m1kkon/fsp-career/actions/runs/38170524774). Проверки используют PostgreSQL 17 и реальный Docker sandbox. Production-сборка Next.js, TypeScript и ESLint завершились успешно; ESLint содержит 24 предупреждения, ошибок нет.

Набор покрывает роли и владельцев записей, подтверждение email, приватность контактов, приглашения и отклики, сохранение профиля, диапазоны зарплат, категорию, историю тестов, конкурентные операции, API, таймауты и исполнение кода в изоляции. Структурный аудит банка проверяет 2359 записей, 559 кодовых задач и 10 выведенных из использования. Дополнительно в указанном CI реально исполнены все 559 эталонных решений и 2881 проверка результата на восьми языках: все прошли. Это отдельная проверка исполнения, а не вывод из структурного аудита.

В локальном браузерном стенде пройден сценарий: публикация задания работодателем → предложение по специализации кандидата → ответ → редактирование условия → проверка первоначального снимка → обратная связь → сохранённое условие и feedback у кандидата. При размере 390 x 844 горизонтальное переполнение отсутствует. Этот результат относится к указанному локальному сценарию, а не к доставке production-почты или внешнему реестру ФСП.

Полный сквозной браузерный прогон последней production-версии не подтверждён; зафиксированы локальные сценарии прежней версии. Реальная доставка production-почты этими сценариями не подтверждалась.

В том же CI проверено конкурентное сохранение профилей во время ожидания judge: 50 аккаунтов и 100 операций сохранения. Сохранения завершились за 146 мс, пока judge оставался в состоянии ожидания. Этот сценарий проверяет сервисные транзакции PostgreSQL, а не HTTP-пропускную способность. Production p95, максимальная пропускная способность и SLA этим тестом не установлены.

Машинные результаты, параметры и хеши реализации хранятся в `docs/current-product-validation.json`, `docs/matching-blend-validation.json` и `docs/full-product-matching-guards.json`. Успешный CI подтверждает указанную ревизию; публикация нового production-релиза проверяется отдельно через `/api/health`.

### 5.2. Синтетическая разметка и стабильность грейда
Для виртуальных профилей разных уровней задана авторская модель вероятности решения задач. Проверяются совпадение ожидаемого и полученного грейда, повторяемость форм, завышение и распознавание Middle; метрики разбиты по уровню. Параметры, формы, агрегаты и хеши воспроизводимого прогона сохранены в `docs/current-product-validation.json`.

| Показатель текущего синтетического holdout | Наблюдённый результат |
|---|---|
| Размер | 1200 виртуальных профилей; два прохождения, 2400 результатов |
| Совпадение с авторским эталоном | 93,17% |
| Совпадение грейда при повторном прохождении | 87,25% |
| Распознавание Middle | 86,50% |
| Завышение относительно эталона | 0,67% |
| Проверки устойчивости модели | Пороговые проверки development/holdout; отдельные случаи только теории, только кодинга и случайного выбора выполнены |

Синтетический holdout отделяет роли/семейства сценариев и формы, но использует ту же авторскую модель ответов. Кодинг моделируется доверенными снимками судьи, не исполняется в этом эксперименте.

Числа относятся к наблюдённому локальному симулятору, не к людям и не к выпущенному production-релизу. Монотонные вероятности виртуальных уровней помогают выявлять ошибки реализации, но не доказывают содержательную сложность банка или реальную психометрическую дискриминативность. Происхождение разметки раскрывается в отчётах. Предыдущие измерения сохранены в `docs/grade-hardening.md` и `docs/synthetic-validation.md`.

### 5.3. Внешний benchmark текстового ранжирования
[Источник Talent-Match](https://github.com/MALINAYAGODA/Talent-Match) содержит 29 вакансий и 656 пар «вакансия - резюме». Основной scope - поддерживаемые направления: **13 вакансий и 348 пар**. Для выбора способа текстового сопоставления используется development: 9 вакансий, 246 пар. Для таблицы ниже используется одно и то же ранее известное holdout: **4 вакансии, 102 пары**, одинаковые пулы кандидатов и бинарные метки `confirmed/failed` для каждого метода. Разбиение не пересекается по вакансиям и резюме. Ревизия источника, SHA-256, seed, хеши реализации и точные агрегаты сохранены в `docs/matching-blend-validation.json`.

Текущий метод согласует свидетельства о типах задач и технологиях, затем ограниченно дополняет их лексической близостью описаний выполненной работы. Веса подтверждённых тестов и ФСП по TalentMatch не подбираются. TF-IDF сравнивает лексические векторы; stack сравнивает пересечение распознанных технологий; random - аналитическое ожидание случайного порядка внутри тех же пулов.

| Метод | P@5 | nDCG@5 |
|---|---|---|
| ФСП Карьера, текущий подбор | **30,00%** | **0,4704** |
| TF-IDF | 25,00% | 0,3366 |
| Пересечение стека | 30,00% | 0,4539 |
| Случайный порядок: ожидаемое значение | 23,36% | 0,2823 |

На этой выборке P@5 текущего метода выше TF-IDF и случайного ожидания, равен пересечению стека; nDCG@5 и MRR выше измеренных baseline. Это сравнение указанных методов, а не утверждение о превосходстве над нейросетями или всеми алгоритмами подбора. Дополнительные метрики рассчитаны для трёх фактически ранжирующих методов:

| Метод | Tie P@5 | R@5 | MRR |
|---|---|---|---|
| ФСП Карьера, текущий подбор | **34,17%** | **39,58%** | **0,8750** |
| TF-IDF | 25,00% | 31,25% | 0,5635 |
| Пересечение стека | 26,67% | 39,58% | 0,7632 |

P@5 - доля положительных меток в первой пятёрке; R@5 - доля всех положительных меток, найденная в первой пятёрке. nDCG@5 учитывает позиции с логарифмическим дисконтированием и нормируется на идеальный порядок. MRR - средняя обратная позиция первого положительного кандидата во всём пуле, без ограничения первой пятёркой. Tie P@5 усредняет порядок внутри равных ранговых групп. Итог каждой метрики - среднее по вакансиям с одинаковым весом вакансии. Для random рассчитываются только показанные аналитические ожидания P@5 и nDCG@5.

Метки `confirmed/failed` отражают скрининг, не факты найма. Резюме заранее отобраны для каждой вакансии, поэтому измерение не характеризует поиск по всему рынку. Holdout мал и ранее изучался; он не объявляется новым независимым финальным тестом. P@5 30% - метрика текстовой выдачи на этих четырёх вакансиях, а не общая оценка продукта или вероятность успешного найма.

### 5.4. Проверка категорий, результатов тестов и ФСП
Подбор по текстам оценивается на TalentMatch; подтверждённые категории, результаты тестов и достижения ФСП проверяются на отдельной авторской разметке, поскольку внешний датасет этих сведений не содержит. В адаптере TalentMatch такие признаки остаются неизвестными и не приносят соответствующих баллов.

В наборе контролируемых функциональных сценариев выполнено **20 из 20 проверок, 0 ошибок**. Подтверждение категории требует явного `verified === true`: отсутствующее значение, строка и число не считаются подтверждением. Проверяются приоритет обязательного грейда над высоким текстовым соответствием, минимумы стажа и языка, отрицания и планы, неизвестная релокация, сумма и границы объясняемых баллов, независимость от входного порядка и приватность контактов. Положительный результат теста повышает соответствующий вклад, но не отменяет обязательные ограничения. Достижение ФСП релевантной дисциплины учитывается выше менее релевантного; скрытая история не влияет на ранжирование; пустая история сохраняет остальные факторы и не исключает кандидата. Источник сценариев и хеши: `docs/full-product-matching-guards.json`.

Ранее использованный авторский набор 24 потребностей и 480 пар служит **контролируемой функциональной регрессией**. Все рекомендации первой пятёрки совпадают с заданным командой эталоном (P@5 100%); объяснения согласованы на 480/480 парах; допуск совпадает с прежней авторской рубрикой на 456/480 парах, недопустимых профилей в первой пятёрке нет. В 24 случаях прежняя рубрика ожидала fail при отсутствии сведений об обязательном навыке, а текущая политика возвращает unknown; эталон сохранён, расхождение не скрыто. Эти сценарии просты и отражают заложенные правила, поэтому результат не является доказательством эмпирического качества подбора на новых людях.

Релевантные профили без истории ФСП допустимы в 24/24 сценариях, входят в первую пятёрку в 22/24. Офлайн-исключение текстовых свидетельств снижает P@5 этой регрессии до 20%; исключение только ФСП или тестовых баллов оставляет P@5 100%, поэтому прирост этих факторов на этой фикстуре не доказан. При одинаковых обязательных фильтрах TF-IDF даёт 57,5%, пересечение стека 80%; это диагностика исполнения собственной рубрики, не внешнее сравнение качества. Метрики, исключения компонентов и границы: `docs/domain-matching-comparison.json`.

И этот регрессионный набор, и двадцать функциональных проверок используют авторские ожидания. Они подтверждают проверенные правила, но не заменяют независимую разметку работодателей, реальный реестр ФСП или измерение качества найма. Их показатели не сравниваются напрямую с TalentMatch.

### 5.5. Новая авторская диагностика переноса
Отдельный набор 8 потребностей и 96 пар проверяет перенос на ранее не использованные при выборе алгоритма сложные описания. Рубрика и данные зафиксированы до первого запуска; реализация зафиксирована до ознакомления автора алгоритма с этим набором. Оценивание выполнено один раз без изменения меток по результату. Это авторская диагностика команды, не реальные участники или независимые работодатели. Протокол, хеши, эталон и результат: `docs/domain-challenge-validation.json` и `docs/matching-blend-freeze.json`.

| Метод | P@5 | nDCG@5 | R@5 | MRR |
|---|---|---|---|---|
| Полный текущий подбор | 42,50% | 0,4117 | 49,38% | 0,4625 |
| Те же фильтры + TF-IDF | 47,50% | 0,5846 | 56,25% | 0,8125 |
| Те же фильтры + пересечение стека | 50,00% | 0,5474 | 60,00% | 0,6667 |

В этом наборе полный метод уступает обоим baseline с одинаковыми обязательными фильтрами по показанным метрикам. Поэтому превосходство над этими методами и качество на рынке не заявляются. Для всех трёх вариантов допуск совпал с рубрикой на 96/96 парах; объяснения полного метода согласованы на 96/96, недопустимых профилей в его первой пятёрке нет.

Положительная метка требует профессиональной релевантности не ниже 2 по авторской шкале 0-3 и допустимости pass. Показанные nDCG@5 бинарные; дополнительно graded nDCG@5 использует линейную шкалу 0-3, обнуляя unknown/fail: полный метод 0,5770, TF-IDF 0,6186, стек 0,6187. Метрики усредняются по потребностям. Из-за числа допустимых релевантных профилей средний достижимый потолок P@5 - 85%, ожидаемый случайный P@5 - 35,42%; ни один показатель не является вероятностью найма.

Известная сложная development-диагностика 12 потребностей/120 пар использовалась при выборе метода: текущий P@5 56,67%, TF-IDF с теми же фильтрами 48,33%; согласованность допуска 115/120. Она не является независимой финальной проверкой. Исходный результат и текущая регрессия сохранены отдельно: `docs/domain-stress-diagnostic.json`, `docs/matching-blend-stress-regression.json`. Параметры отбора вариантов и компромиссы метрик раскрыты в `docs/matching-blend-experiment.json`.

## 6. Предполагаемая интеграция ФСП
Текущий `lib/fsp.mjs` - демонстрационный серверный адаптер на собственных фикстурах. Источник помечен `demo` в интерфейсе и PDF. Есть 44 тестовых ID; несколько возвращают пустую историю. Наличие ID не является подтверждением принадлежности реальному участнику. Отсутствие истории не блокирует регистрацию, тест, поиск и контакт; бонус ФСП отсутствует, остальные факторы сохраняются.

Предлагаемая запись достижения: ID события, дисциплина, год, результат, уровень, командный/индивидуальный формат, источник и время проверки. Из публичной проекции исключается неподтверждённая ручная подмена достижений. История усиливает рейтинг до 6 баллов, не назначает грейд и не отменяет согласия владельца.

Будущий адаптер получает контракт и основание доступа от ФСП. После OIDC/Keycloak-проверки владения идентификатором сервер нормализует достижения и хранит происхождение, дату синхронизации и состояние актуальности. При временном сбое последняя подтверждённая история помечается устаревшей: ошибка источника не превращается в «достижений нет». Нужны отзыв согласия, журнал изменений, повторы синхронизации и тесты пустого/недоступного реестра. Реальные endpoint, scopes и форматы ответов уточняются после предоставления контракта реестра ФСП.

## 7. Концепции ATS и защиты от фиктивных предложений
### 7.1. ATS
Граница интеграции - корпоративный API-ключ с минимальными правами и конкретной компанией. До согласия кандидата ATS получает только разрешённую обезличенную проекцию. После принятия предложения или самостоятельного отклика экспортируются согласованные контакты, предложение и статус; сопоставление использует внешние ID, а не email как глобальный ключ.

Промышленный коннектор предусматривает очередь исходящих событий, подпись HMAC, `eventId` и ключ идемпотентности, экспоненциальные повторы, dead-letter очередь, журнал доставки и endpoint повторной синхронизации. Входящие изменения проверяют компанию, допустимый переход статуса и версию записи; устаревшее событие не откатывает новый статус. Отзыв ключа/согласия запрещает следующие выгрузки. Минимальный контракт событий: invitation.sent/viewed/accepted/declined, application.created/statusChanged и consent.revoked. Публичный API v1 реализован. Внешний ATS-коннектор и очередь webhook описаны как архитектура следующего этапа; промышленная интеграция с конкретной ATS не подключена.

### 7.2. Антифрод работодателей
Предлагается поэтапная схема: подтверждённый email, доказательство владения корпоративным доменом, проверка реквизитов при повышении лимитов, прозрачная метка уровня проверки. Риск оценивается по массовым однотипным предложениям, аномальным условиям, повторным жалобам и изменениям домена/контакта. Сигнал не означает автоматическое признание мошенничества: спорные случаи проходят ручную модерацию с возможностью обжалования.

Ограничения: лимиты приглашений и публичных публикаций, запрет приглашений от заблокированной компании, кнопка жалобы с сохранением доказательств, журнал решений и срок пересмотра. Сбор минимальных данных и контролируемый доступ к жалобам предотвращают превращение антифрода в публичный список обвинений. Верификация юридических лиц и очередь модерации описаны как следующий этап, не как уже подключённый сервис.

## 8. API и безопасность
Публичная API: `https://fspcareer.space/api/v1`. Руководство: `/api-docs`; машинный контракт OpenAPI 3.1: `/api-v1.openapi.json`. Внутренний контракт кабинета: `/openapi.json`. Все актуальные схемы и коды ошибок публикуются в репозитории; генератор `scripts/generate-public-api.mjs` поддерживает согласованность руководства и схем.

API-ключи создаются после входа с подтверждённым email, имеют права чтения/записи и срок 30/90 дней; полный ключ показывается один раз. Передавайте ключ в `Authorization: Bearer KEY`, храните его на сервере интеграции. Роль, владелец и доступ к контакту проверяются при каждом запросе.

| Группа | Назначение и контракт |
|---|---|
| `/api/session` | Регистрация, вход, подтверждение, выход и восстановление; cookie-сессия. |
| `/api/state`, `/api/action` | Кабинет: собственное состояние и разрешённые бизнес-действия, включая тестирование и задачи. |
| API v1: `/state`, `/me`, `/candidates` | Состояние, профиль владельца, разрешённый каталог и объяснимые фильтры. |
| API v1: `/jobs`, `/needs`, `/invites`, `/applications` | Вакансии, подборки, предложения и статусы; ограничения доступа сохраняются. |
| API v1: `/tasks`, `/submissions`, `/messages` | Задания, ответы и переписка только доступных участнику записей. |
| `/api/health` | Статус и ревизия релиза; не публикует секреты и персональные данные. |

Успешные ответы - JSON UTF-8, ошибки различают некорректный ввод, отсутствие входа, запрет, отсутствующий ресурс и конфликт состояния. Точные тела, обязательные поля и числовые HTTP-коды смотрите в OpenAPI и `docs/api.md`; документация не заменяет runtime-проверку. Приглашения и вакансии требуют целочисленный положительный диапазон зарплат; неоднозначные десятичные суммы отклоняются.

Пароли: scrypt и индивидуальная соль; сессии и одноразовые токены хешируются; cookie HttpOnly/Secure в production; отправляемые почтовые данные шифруются. Сервер проверяет Origin, доступ к владельцу и согласия. Пользователь может ограничить публикацию и убрать связь ФСП. Указанные механизмы являются техническими мерами защиты. Юридическое соответствие 152-ФЗ, сведения об операторе, размещение и сроки хранения зависят от фактической модели эксплуатации; результаты автоматических проверок не являются юридическим заключением.

```sh
node --env-file=.env.local scripts/send-mail.mjs
```
Откройте http://localhost:3000. Последняя команда делает один проход почтовой очереди; для непрерывной доставки нужен планировщик. Не подставляйте production-базу в тесты. Подтверждение email выполняется по одноразовой ссылке через настроенную почтовую службу.

### 10.2. Проверки и production build
```sh
npm run build
npx tsc --noEmit
npm run lint
npm test
npm run bank:audit
```
TypeScript запускается после сборки клиентского манифеста. PostgreSQL-тесты требуют `TEST_DATABASE_URL` отдельной базы с окончанием `_test`; реальные sandbox-тесты требуют Docker и `CODE_SANDBOX_TESTS=1`. Конкретные команды образа и worker приведены в `docs/coding-and-role-grades.md`. Без этих компонентов соответствующие проверки помечаются как пропущенные.

### 10.3. Docker и сервер
Создайте защищённый `.env` на сервере: `SITE_DOMAIN`, `POSTGRES_PASSWORD`, Resend, `EMAIL_FROM`, `MAIL_TOKEN_KEY`; при отдельном worker также `CODE_SANDBOX_URL` и `CODE_SANDBOX_TOKEN`. Полный список и порядок GCP/IAP описаны в `docs/deployment.md`.

```sh
docker compose build
docker compose up -d
docker compose ps
curl --fail https://YOUR_DOMAIN/api/health
```
Compose сначала ждёт PostgreSQL, выполняет миграции, затем запускает приложение и Caddy. Ответ `/api/health` идентифицирует установленную ревизию. Эксплуатация предусматривает резервное копирование PostgreSQL, проверку восстановления на отдельной базе, аутентификацию приватного worker и мониторинг доставки почты. Выполнение миграций и обновление приложения входят в отдельную процедуру выпуска.
