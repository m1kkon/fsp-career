Дата проверки: 10 октября 2026. Исходная реализация: коммит `f4e6a1e7e56602ffec1cac1233fad3d758d9d8f0`. Состояние «после» относится к промежуточной реализации v2, которая затем была заменена v3 в рабочем дереве. Машинный отчёт до/после: [synthetic-validation-results.json](synthetic-validation-results.json).

## Результат

На фиксированных синтетических сценариях улучшились релевантность первых результатов, соответствие заданному грейду и повторяемость оценивания. **Это проверка реализации и предварительная калибровка симулятора, а не доказательство качества на реальных кандидатах.** Middle и повторяемость остаются ограничениями.

| Метрика, весь набор | До | После |
|---|---:|---:|
| Доля релевантных среди первых пяти, P@5 | 20,0% | 97,5% |
| Качество порядка первых пяти, бинарный nDCG@5 | 19,9% | 98,3% |
| nDCG@5 с трёхуровневой релевантностью | 46,6% | 98,9% |
| MRR, положение первого релевантного кандидата | 44,4% | 100,0% |
| Совпадение грейда с заданным прототипом | 52,8% | 86,3% |
| Cohen κ для заданного и полученного грейда | 0,371 | 0,818 |
| Один грейд в двух прохождениях одного профиля | 62,4% | 78,5% |
| Завышенный грейд | 0 / 4 800 | 1 / 4 800 |
| Неверная классификация обязательных условий | 0 / 480 | 0 / 480 |
| Не прошедшие обязательные условия в первых пяти | 0 | 0 |

Бинарная релевантность: подходит к задачам и соблюдает обязательные условия. Навыки без подтверждения релевантного опыта имеют промежуточную метку 1, но не считаются релевантными для P@5. Для градуированного nDCG используются исходные метки 0/1/3 с линейной выгодой. Средний Recall@5 после исправления — 75,4%: в каждом пуле есть 6–7 релевантных профилей, все они не могут попасть в пять мест. Ожидаемый P@5 случайного порядка — 32,5%.

## Данные и разделение

Разметка задана в `scripts/benchmarks/fixtures/synthetic-v1.mjs` до запуска исходной реализации. Фикстуры не импортируют производственные функции подбора или оценивания; метки не строятся из полученного системой балла. Они выражают авторскую рубрику проверки, без независимой экспертной разметки.

Подбор: **24 потребности, по 20 профилей, 480 пар**. Шесть семейств задач, Junior/Middle и тексты опыта на русском/английском. Проверяются работа и проекты, грейд выше минимума, отсутствие ФСП, подтверждённое демодостижение, касание зарплатных диапазонов, перечень навыков без опыта, нерелевантные задачи, отрицание опыта, будущие планы, другая специализация, низкий/неподтверждённый грейд, отсутствующая технология, бюджет, английский, стаж и формат. Обязательные условия включают неизвестные значения: `pass`, `unknown`, `fail` проверяются отдельно.

Грейды: **2 400 виртуальных профилей, по два прохождения, 4 800 результатов ролей**. Для каждой из шести ролей моделируются по 100 профилей четырёх прототипов. Это многократные случайные реализации четырёх моделей, не 2 400 независимо размеченных людей. Используются фактические банк вопросов, сборщик адаптивных вариантов, маршрутизация, оценка модулей и правило всех обязательных модулей роли. На модуль создаётся 20 вариантов; варианты в повторных прохождениях могут пересекаться.

Вероятности правильного теоретического ответа и полного решения кодинга заданы независимо от формулы Rasch продукта:

| Прототип | Теория, сложности 1/2/3 | Полное решение кодинга, сложности 1/2/3 |
|---|---|---|
| Ниже Junior | 0,45 / 0,20 / 0,08 | 0,25 / 0,05 / 0,01 |
| Junior | 0,88 / 0,60 / 0,25 | 0,88 / 0,25 / 0,04 |
| Middle | 0,96 / 0,85 / 0,58 | 0,97 / 0,86 / 0,35 |
| Senior | 0,99 / 0,97 / 0,91 | 0,99 / 0,97 / 0,90 |

Добавляется фиксированная вариация семейства вопросов до ±0,06. Не полностью решённая задача может иметь частичный зачёт или пропуск; проверки одной задачи не моделируются как независимые случайные успехи. Результаты судьи моделируются доверенными снимками: **этот benchmark не исполняет код в sandbox**.

Development: Backend/платежи, QA/регрессия, Data Science/аналитика. Holdout: Frontend/доступность, DevOps/надёжность, ML Engineering/serving. Семейства и идентификаторы профилей не пересекаются. Вероятностная модель ответов общая; отложенные роли проверяют перенос между ролями и задачами, не независимую популяцию людей.

Сначала зафиксированы исходные метрики. Ошибки и восемь вариантов политики исследованы только на development. Затем политика зафиксирована и открыта holdout-часть. После просмотра holdout параметры не менялись.

| Набор | P@5 до → после | Совпадение грейда до → после | Повторяемость до → после |
|---|---:|---:|---:|
| Development, 240 пар / 2 400 попыток | 20,0% → 95,0% | 49,7% → 84,5% | 63,9% → 76,5% |
| Holdout, 240 пар / 2 400 попыток | 20,0% → 100,0% | 55,9% → 88,1% | 60,8% → 80,5% |

100% на контролируемой holdout-выборке подбора не означает 100% на реальных резюме.

## Исправления подбора

1. Грейд в форме является минимумом. Подтверждённый Senior получает полные баллы при запросе Middle; штраф за превышение минимума устранён.
2. Реальный опыт выполнения задач и проекты получают до 20 баллов вместо 8. Тест — до 12 вместо 20, ФСП — до 6 вместо 10. Общая сумма остаётся 100. Достижения и высокий тест больше не так легко вытесняют релевантный опыт.
3. Отрицание опыта и будущие планы не считаются выполненной работой. Добавлено распознавание английского множественного `APIs`.
4. Шкала тестовой составляющей начинается с нового стандартного порога 40. Объяснения и максимумы баллов без запроса вычисляются согласованно с текущими весами.

Обязательные фильтры сохраняют приоритет над баллом. Кандидат без истории ФСП может набрать 94/100. Каждый итог проверяется как сумма отображаемых слагаемых; диагностическая текстовая схожесть не задаёт порядок самостоятельно. Демопрофили не изменялись для улучшения метрик, benchmark-профили не загружаются в каталог.

## Исправления грейдов

Сильная теория при слабой практике отправляла профиль в сложную ветку, где не было возможности подтвердить базовый практический уровень. Для новой политики сложная ветка требует не только маршрутизационный балл ≥65, но и одно полное решение кодинга первой части. Исходные пороги часто занижали заданный уровень; добавлены отдельные минимумы теории и обновлены общие/практические пороги.

| Грейд | Общий балл | Теория | Кодинг | Полностью решённая задача |
|---|---:|---:|---:|---|
| Junior | ≥40 | ≥35 | ≥30% | ≥1 сложности 1 или выше |
| Middle | ≥60 | ≥55 | ≥50% | ≥1 сложности 2 или выше |
| Senior | ≥85 | ≥75 | ≥75% | ≥1 сложности 3 |

Все условия обязательны в каждом модуле роли. Полностью правильная теория без кодинга, кодинг без теории и частичные решения без одного полного решения не подтверждают грейд.

Development-калибровка:

| Вариант | Совпадение грейда | Повторяемость | Завышение |
|---|---:|---:|---:|
| Исходные правила | 49,7% | 63,9% | 0% |
| Только общие пороги 45/65/85 | 53,1% | 62,1% | 0% |
| Пороги 45/65/85, кодинг 40/50/75 | 72,7% | 69,8% | 0,042% |
| Пороги 40/60/85, кодинг 30/50/75 | 79,3% | 70,9% | 0,167% |
| Только практическая готовность ветки | 52,7% | 62,8% | 0% |
| Готовность + пороги 45/65/85 | 76,1% | 69,5% | 0,042% |
| Готовность + пороги 40/60/85 | 84,8% | 76,9% | 0,167% |
| **Выбрано: предыдущий вариант + минимум теории** | **84,5%** | **76,5%** | **0,042%** |

Выбран вариант с отдельными защитами теории и практики; небольшое снижение accuracy относительно незащищённого варианта принято сознательно. Это ограниченный набор гипотез, не глобальный оптимум.

На этом этапе правила были версионированы как `rasch-theory-practice-v2`, суточный пул — `mixed-v5-synthetic-calibration`. Уже начатые попытки и старые результаты сохраняют снимки исходных правил. Для сохранённых старых спецификаций создаётся новая версия; нестандартные общие пороги мейнтейнера не заменяются. Текущая политика v3 описана в [scoring.md](scoring.md); приведённые выше проценты кодинга относятся к прежней линейной шкале v2.

## Что ещё не подтверждено

Распознавание заданного уровня: ниже Junior — 100%, Junior — 84,5%, **Middle — 69,3%**, Senior — 91,4%. У Middle 367 из 1 200 попыток получают более низкий уровень, одна — более высокий. Общая повторяемость 78,5% означает изменение грейда в 21,5% пар прохождений. Wilson-интервал повторяемости в рамках симулятора: 76,8–80,1%; он не учитывает ошибку выбранной модели человека.

Из 1 908 встретившихся вопросов 1 889 имеют достаточно наблюдений для сравнения сильных/слабых прототипов. Средняя разница долей успеха — 0,471, отрицательных значений нет. Это проверка поведения симулятора: вероятности по уровню заданы возрастающими. Она **не подтверждает содержательную сложность или реальную дискриминативность банка**.

Для окончательной валидации необходимы ответы реальных людей, независимый экспертный грейд и разметка реальных пар «потребность — резюме». Приоритет: Middle, пограничные результаты и согласованность вариантов. На синтетическом тесте этого этапа можно подтверждать исправление выявленных ошибок реализации; заявлять доказанную профессиональную квалификацию нельзя. Актуальные значения Middle и повторяемости v3 приведены в [grade-hardening.md](grade-hardening.md).

Отчёт содержит хеш каждого исходного файла, версии политик, seed-идентификаторы, матрицы ошибок, метрики ролей и списки разобранных случаев подбора. Подробные отчёты в игнорируемом `output/validation` дополнительно сохраняют промежуточные результаты и состав вариантов; ответы воспроизводятся по фиксированным seed. Подмена источника случайности действует только внутри синхронной offline-сборки и немедленно восстанавливается; production-генератор не меняется.

Запуск `synthetic-validation.mjs` из текущего дерева использует текущие `lib` и спецификации v3. Параметр `--label` меняет подпись отчёта, **не версию оценивания**. Поэтому такой запуск не воспроизводит историческое состояние «после» v2.

Для повторения исходного состояния взять `lib` из указанного baseline-коммита в отдельный каталог. Для состояния «после» требуется сохранённая копия `lib` v2 с хешем `20862d…`; локальный архив находится в игнорируемом `output/validation/grade-v2/source`. Этот архив не поставляется с чистым клоном репозитория. В оба каталога скопировать одну и ту же версию `scripts/benchmarks` и предоставить те же зависимости. Не переносить исправленные `lib` в baseline. Запустить benchmark в каждом каталоге с `--split all`; оба отчёта обязаны иметь один хеш фикстуры, а исходники — соответствующие хеши «до» и «после» выше.

Пример для заранее подготовленного архивного каталога v2; пути подставляются вручную:

```sh
node /path/to/archived-v2/scripts/benchmarks/synthetic-validation.mjs --label historical-v2 --split all --output output/validation/synthetic-v2-replay
node scripts/benchmarks/compare-validation.mjs before/report.json output/validation/synthetic-v2-replay/report.json output/validation/synthetic-v1-v2-replay.json
```

`calibrate-synthetic-grades.mjs` — отдельная development-диагностика ограниченных вариантов с принудительным линейным правилом v2. Она не меняет рабочую политику и не заменяет полный отчёт состояния «после». Исторический JSON сохраняется; повторные результаты следует записывать в `output/validation`.

Для проверки текущей реализации v3 без подмены исторического отчёта:

```sh
node scripts/benchmarks/synthetic-validation.mjs --label current-v3 --split all --output output/validation/synthetic-current
node --test tests/synthetic-validation.test.mjs
```

Тесты в текущем дереве проверяют актуальную реализацию. Более широкая свежая проверка v2 → v3, её ограничения и команды описаны в [grade-hardening.md](grade-hardening.md).

Определения: [Cohen κ](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.cohen_kappa_score.html) учитывает случайное совпадение; [nDCG](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.ndcg_score.html) учитывает положение релевантных результатов. Метрики реализованы локально и проверены независимыми небольшими примерами; accuracy, κ, повторяемость и P@5 дополнительно сверены вычислением на Python.
