# ФСП: демонстрационный адаптер и будущая интеграция

Актуализация: 10 октября 2026 года. Реальный реестр ФСП не подключён; достижения имеют демонстрационное происхождение. ТЗ намеренно не предоставляет API и структуру реестра, поэтому MVP показывает предложенную модель на собственных данных. Отсутствие ФСП ID и пустая история не блокируют регистрацию, оценивание, каталог, PDF или приглашения.

## Текущий контракт внутри приложения

[`lib/fsp.mjs`](../lib/fsp.mjs) — серверный mock-adapter без внешних запросов. `FSP_DEMO_IDS` содержит 44 ID, от `DEMO-FSP-001` до `DEMO-FSP-044`: первые 14 сохранены для совместимости, остальные связаны с расширенными демонстрационными кандидатами. Другой ID отклоняется. Это перечень фикстур, а не формат реального идентификатора Федерации.

`profile.fsp` содержит `id`, `source: 'demo'`, `status: 'demo'`, `linkedAt` и `achievements`. Событие включает ID, название, дисциплину, год, результат, командный/индивидуальный формат, нормализованный уровень (`winner`, `prize`, `final`, `participant`) и источник. Конкретные даты и подтверждающие ссылки не выдумываются.

Действия `fsp-link` / `fsp-unlink` доступны только владельцу кандидатского профиля. Каноническая публичная проекция заново получает события из адаптера по ID: произвольные поля, подменённый источник или вручную исправленное достижение не принимаются. `fspVisible` отдельно отключает публикацию истории, в том числе её вклад в подбор. В карточках, деталях и PDF источник обозначается как тестовый. Контакты кандидата раскрываются по собственным правилам приглашения/отклика, а не из-за наличия ФСП.

`DEMO-FSP-004`, `007` и `008` дают пустую историю; `DEMO-FSP-011` содержит два события прошлых лет. Один ID разрешено привязать к нескольким тестовым аккаунтам: настоящий владелец не проверяется, и такая связь не должна называться реестровой верификацией.

## Вклад в ранжирование

[`fspSignal`](../lib/matching.mjs) получает только видимую каноническую историю. Максимальный вклад — **6 баллов из 100** для подтверждённой потребности. Без достижений доступны остальные **94 балла**. ФСП не присваивает грейд и не заменяет тесты.

Для каждого события:

- уровень: победа `1`, призовое место `0,85`, финал `0,6`, участие `0,35`;
- профильность дисциплины для специализации: `0,7–1` по заданной таблице;
- давность по году UTC: до двух лет `1`, до четырёх лет `0,75`, старше `0,5`.

Произведение округляется до сотых. Лучшее событие учитывается целиком; каждое дополнительное событие добавляет `0,1` к силе истории, итог ограничен `1`. Баллы равны `round(6 × сила)`. Это дополнительный бонус за число событий, а не суммирование полных баллов всех достижений.

В объяснении доступны события и источник. Без потребности интерфейс показывает только сумму **«Тесты и ФСП» до 18**: тест до 12 и ФСП до 6; общий балл соответствия из 100 не вычисляется. При наличии потребности обязательные условия имеют приоритет над суммарным баллом. Явный фильтр работодателя «с достижениями» может сузить каталог; само отсутствие истории по умолчанию человека не исключает.

Таблица дисциплин и веса — гипотеза MVP, проверенная на авторских синтетических сценариях, а не измеренная причинная связь достижений с успешностью найма. Нельзя утверждать, что один вопрос теста всегда ценнее конкретного спортивного результата: вклад теста зависит от нормализованного итогового балла, а не фиксированного веса одного ответа. См. [подбор и ограничения](matching-benchmark.md) и [синтетическую проверку](synthetic-validation.md).

## Проект следующего этапа

После согласования с ФСП потребуются:

1. Контракт реестра и основание доступа: какие дисциплины/события/результаты доступны, кому и с каким согласием.
2. Проверка принадлежности ID аккаунту. OAuth/OIDC с будущим Keycloak — возможный подход, а не уже согласованная схема или текущий способ входа.
3. Серверный адаптер с нормализацией, происхождением, временем проверки, поддержкой отсутствия истории и ошибками источника.
4. Отдельное хранение реестровых данных и самоописания, синхронизация, отзыв доступа, журнал изменений и стратегия устаревших данных.
5. Проверки владения, приватности, повторной доставки, удаления/отзыва, недоступности реестра и влияния данных на подбор.

Предлагаемая стратегия при сбое: хранить последнюю успешно проверенную историю с датой и признаком устаревания; не превращать сбой в «достижений нет». В MVP этот механизм реальной синхронизации ещё отсутствует. Демонстрационная связь автоматически не становится настоящей при замене адаптера. Конкретные endpoint, OAuth scopes и форматы ответа пока неизвестны.

Текущая email/пароль авторизация через Resend независима от будущего ФСП-входа. Категория по специализации и грейду определяется тестированием; история соревнований обогащает профиль.

## ATS и защита от недобросовестных работодателей

По §2 ТЗ это развитие за пределами MVP: ожидается концепция. Структурированная анкета (`lib/ats.mjs`) и API v1 с ключами уже существуют; название поля `ats` не означает подключённую внешнюю ATS.

Предполагаемый коннектор экспортирует согласованные контакты и статусы после принятия приглашения/отклика. Для промышленного обмена нужны модель разрешений, подписанные webhook, идемпотентность, очередь доставки/retry, аудит и отзыв ключей. Реальная ATS и эта схема webhook пока не подключены. Текущий HTTP API описан в [API](api.md) и [публичном руководстве](../public/api-guide.md).

Концепция антифрода включает проверку владения доменом компании, сигналы жалоб, ограничения приглашений и очередь модерации. Email подтверждает адрес аккаунта, но не проверяет юридическое лицо или добросовестность компании. Эти дополнительные механизмы не объявляются реализованными.
